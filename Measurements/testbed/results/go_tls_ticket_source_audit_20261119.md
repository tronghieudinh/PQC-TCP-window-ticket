# Where does Go's crypto/tls write the TLS 1.3 session ticket? Source reading, 19 November 2026

Read, then confirmed by `go_calibrate.py` (the write sizes of `tls_probe_go`, `results/go_calibration.json`). Source: Go 1.27.4 (`GOROOT/src/crypto/tls`, `VERSION` time 2026-11-02). The case is the one of L1: TLS 1.3, server with `ClientAuth = RequireAndVerifyClientCert`, full handshake and resumption (PSK).

## Server: when the ticket is written
- `handshake()` (`handshake_server_tls13.go:66-97`): `c.buffering = true` (before `sendServerParameters`), then ServerHello, EncryptedExtensions, Certificate, CertificateVerify and Finished are appended to `c.sendBuf`, and `c.flush()` writes the buffer with ONE `conn.Write` (`conn.go:947-968`: `write` appends while buffering, `flush` writes the whole buffer and clears `buffering`). Then `readClientCertificate`, then `readClientFinished`.
- `sendServerFinished` ends with: if no client certificate is requested, `sendSessionTickets()` is called there, INSIDE the buffered flight (`handshake_server_tls13.go:929-935`). `requestClientCert()` is `ClientAuth >= RequestClientCert && !usingPSK` (`:821-823`): it is false on every resumption (PSK). So on a resumed connection the NewSessionTicket record is appended to the server's first flight and leaves in the same write, before the client's Finished is read. The calibration shows exactly that: one write of 10 293 B (ML-DSA-44) holding ServerHello ... Finished and the ticket.
- Full handshake under mutual TLS: the ticket is sent from `readClientCertificate`, after the client's Certificate and CertificateVerify have been read and verified and before `readClientFinished` (`:1112-1118`), as a write of its own (the flush has already cleared `buffering`). In the L1 tests the client's flight (Certificate, CertificateVerify, Finished) arrives together, so the ticket leaves when it arrives.
- Number: one ticket per connection ("we only ever send one ticket per connection", `sendSessionTicket`, `:972-1020`); sent only if tickets are not disabled and the client offered `psk_dhe_ke` (`shouldSendSessionTickets`, `:941-953`). A new ticket is issued on a resumed connection too. The only built-in switch is `SessionTicketsDisabled`, which also stops resumption; `WrapSession` cannot skip a ticket (an error from it terminates the connection, `common.go`, comment of `WrapSession`), so "no ticket on resumption" needs a patched library.

## What the ticket holds
- `sessionState()` (`ticket.go:298-312`): the peer certificates (`peerCertificates`: for the server, the client's chain as sent), the OCSP response, SCTs and `verifiedChains`. Marshalling (`ticket.go:128-160`): the peer certificates once and, for every verified chain, all certificates but the leaf. Under mutual TLS with a depth-1 chain that is the client's leaf plus the trust anchor: 1.8 to 16 KB for the four suites of L1 (calibration: 1 787, 8 980, 12 038, 15 954 B).
- On resumption the server rechecks the stored chains (`checkForResumption`, `:340-392`: certificate not expired, `anyValidVerifiedChain` against `ClientCAs`): CPU only, no write.

## Client
- The ClientHello is written without buffering, one `Write` per record of at most 2^14 bytes (calibration: 16 389 + 2 921 B for ML-DSA-44 suites above one record), so the ticket the ClientHello carries back makes it 2 to 13 segments. The Finished is a write of its own (64 B), the request follows as application records.
- `DynamicRecordSizingDisabled` affects only application-data records (`conn.go:900-903`); handshake records are always up to 2^14. The probe sets it on both sides, so the response leaves as 16 KB records, as with OpenSSL.

## DTLS and QUIC
- DTLS: `crypto/tls` has no DTLS (no file or identifier in `GOROOT/src/crypto/tls` mentions it). There is nothing to read; DTLS libraries are other projects.
- QUIC: the tickets are NOT sent automatically. With a `QUICConn`, `shouldSendSessionTickets` is false (`handshake_server_tls13.go:946-949`) and the application must call `QUICConn.SendSessionTicket` after the handshake is complete (`quic.go:319-338`): once per connection (a second call is an error), and it does nothing if `SessionTicketsDisabled`. So the position of the ticket in a Go QUIC server is chosen by the application (in practice a QUIC library right after the handshake-complete event), and the packetisation of the TLS bytes (CRYPTO frames, the 3x anti-amplification limit before address validation) is done by that library, not by `crypto/tls`, which only hands out bytes per encryption level. On the client the session reaches the cache through `QUICConn.StoreSession` (`:340-356`). Nothing of this was measured; the G10 results say nothing about QUIC. (The simulator has a QUIC mode with the amplification limit, `pqc_sim.py`, not validated against a real QUIC stack.)

## Application settings that change the result (`common.go`, `ticket.go`)
| Setting | Effect on position, number or size of the ticket |
|---|---|
| `ClientAuth` (server) | `NoClientCert`: `requestClientCert()` is false also on a full handshake, so the ticket is appended to the first flight there too, and holds no client certificate (a few hundred bytes plus 48 B of ticket encryption). `RequestClientCert` and above: as in G10 (first flight on resumption; after the client's Certificate on a full handshake). A resumed session whose stored client chain no longer verifies is refused (`checkForResumption`). |
| `SessionTicketsDisabled` | no tickets and no resumption (server), no resumption (client). |
| `SetSessionTicketKeys` / `SessionTicketKey` | only the encryption (16 B IV + 32 B HMAC around the state, `encryptTicket`); with the key left at zero Go rotates it daily and drops it after seven days. G10 sets a fixed key. |
| `WrapSession` / `UnwrapSession` | the content: the application may keep the `SessionState` on the server and return a short handle, so the ticket (and the resumption ClientHello) becomes tiny while the position stays the same. This is the setting that would turn Go's large tickets into small ones; it is the ONLY way to vary the ticket size in Go without patching the library (an option for a later experiment: same library, same position, small ticket). |
| `ClientSessionCache` (client) | none: without it the client does not resume. The cache is keyed by `ServerName`; a session is single-use in TLS 1.3 (`Put(key, nil)` after use). |
| `GetConfigForClient` | per-client override of all of the above. |
| `DynamicRecordSizingDisabled` | affects application data only (`conn.go:900-903`). Left at its default (false), a Go server sends the first 128 KB of application data on a connection in records of 1 208 B on the wire (`tcpMSSEstimate`, `recordSizeBoostThreshold`, `conn.go:876-881`), i.e. smaller than a 1 440-byte segment: the response then needs more segments than the model counts (the model's `app_records` splits at 16 KB). G10 disables it on both sides; a typical Go server does not, so the G10 predictions apply to that default only after a re-derivation of the response writes. |

## Read against L1
Go differs from OpenSSL, GnuTLS and wolfSSL (see `tls_libs_ticket_source_audit_20261119.md`) in where it writes the ticket on a resumption (with the first flight) and in what it stores (certificates twice, 1.8 to 16 KB). That is why the G10 model has two positions to compare, `go` and `joined`, with the sizes of the calibration. Limits of this note: source reading of one release (Go 1.27.4); the QUIC path read only inside `crypto/tls` (the QUIC library that calls it was not); the settings above change position, number and content of the ticket, so the G10 numbers describe the default configuration of the probe (mutual TLS, fixed ticket keys, dynamic record sizing off), not Go servers in general.
